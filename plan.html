Wexa AI take-home · CognoDB

Cartograph

A codebase and its history loaded into a graph database, then handed to an AI. We build the map and the roads. We do not build the driver — any model, through the built-in chat or through MCP, does the reasoning by calling our queries as tools.

2026-08-15 6 phases db: CognoDB (openCypher / Bolt) name: working title

The product in one sentence. Point it at a repository — a GitHub URL, a local folder via CLI, or a dropped folder — and it builds a graph of every file, symbol, call, import, commit and author. Then you explore that graph visually, or ask an AI about it in plain English.

The bet. Most "code intelligence" tools bake in opinions: what's risky, what a module means, what you should do. We store facts and expose traversals. The intelligence is rented, not built — which is why the scope stays small and why the product gets better every time the models do.

Revisions — grilling session, 2026-08-15. The decisions below supersede anything later in this document they contradict. Kept as a visible log because the reasoning is interview material.

Stack. Node · pnpm · React (Vite) · NestJS — not Bun / Turborepo / Next.js. Package manager is pnpm; monorepo via pnpm workspaces. All bun run commands below read as pnpm.

Deploy. Frontend on Vercel; API + worker on Azure Container Apps as one container app, min = max = 1 replica. git must be installed in the Dockerfile (slim/alpine base images omit it). No scale-to-zero (a polling worker must stay alive).

Ingestion queue. BullMQ + free Redis (REDIS_URL, e.g. Upstash) — this replaces the in-memory job store idea entirely. Worker lives in the same Nest deploy but uses a sandboxed / forked processor so CPU-heavy ts-morph parsing runs in a child process and never blocks the API event loop. Worker concurrency 1 (respects CognoDB c0). Redis does the locking, so scaling replicas is safe later; single replica for now by choice, not necessity.

Ingestion is core, not last. The landing page leads with a "paste a GitHub URL" box, so live ingest is promoted ahead of the old phase 6: a minimal happy-path ingest (URL → job → clone → extract → load → phase streaming, guardrails only) ships as phase 4a, before the UI polish in 4b. Folder drop, eviction, and polished rejection copy remain the cuttable tail. The §08 cut-list rationale "nobody knows it was meant to do more" is now void.

MCP moves early. Built right after the query layer (phase 3), not bundled with chat. It is the most on-brand surface for Wexa (structured context for coding agents) and is nearly free once packages/tools exists. Chat stays later and is the first AI surface cut.

Chat model. The chat tool-use loop runs on Groq with an open gpt-oss model (OpenAI-compatible API) — cheap and fast, and plenty for composing fixed, tested queries. The env var is GROQ_API_KEY, not ANTHROPIC_API_KEY. MCP needs no model key of ours: it only exposes the tools, and the user's own agent (Claude Code, Cursor, etc.) supplies the reasoning.

Seed repos. Swap zod (a library with no routes and only ~40 huge files) for a real TypeScript web app — papermark / dub / formbricks / inbox-zero, whichever lands nearest 600–900 files under the size caps. Keep hono and drizzle-orm. This gives Entrypoint / HANDLED_BY real data and the map a proper node count. Demo data is committed as seed/*.json (loaded at deploy); the live worker calls the identical extractor + loader, so the seed proves the pipeline.

Map — two shapes. Overview = circle-packing bubbles (d3-hierarchy pack, styled with shadcn tokens, import arcs shown on hover only — not the force-directed hairball). Focus view = force-directed on the 20–80 node neighbourhood, where the depth slider lives. UI is React + Tailwind + shadcn, one global light/dark theme; CSS variables must be fed into the graph canvas or it won't follow the theme.

Balance & honesty. Code structure and people get equal weight (structure is the stronger graph argument; ownership makes it legible). Call resolution skips ambiguous calls rather than guessing, and the coverage % ("1,240 of 1,680 calls traced") shows on the dashboard and is fed into every AI tool result. Query set follows what the views + assignment need — must include the depth traversal and at least one SQL-awkward query (cycles / coupling); coupling default depth ~2, tuned against the seed repos.

Query wiring. Shared registry (one {name, description, params: zod, cypher, map} per query), thin Nest host: one generic POST /api/query/:name controller, chat and MCP iterate the same registry. Fallback if it clogs: split into per-query Nest controllers that import the same def — documented as the escape hatch, not built now.

00Decisions locked

Resolved during design. Each one removes work rather than adding it. These are also the answers to give in the follow-up interview, so they need to be defensible, not just convenient.

  • No inferenceThe graph stores only facts AST output and git log output. No LLM-named clusters, no computed "risk score", no Feature nodes, no opinions persisted as data. If we can't point at the line of source or the commit it came from, it doesn't go in the graph.
  • Aggregation ≠ intelligenceSums and decay stay in Cypher Weighted contribution per author is SUM() with a time decay — the same thing you'd write in SQL. It lives in the query layer because the alternative is dumping 8,000 commit rows into a context window and asking a model to do arithmetic.
  • LanguageTypeScript / JavaScript only One extractor, done well, using ts-morph. Stated up front in the UI and README. A half-working multi-language extractor is worth less than one honest one.
  • Code depthFile and top-level symbol No expression-level analysis, no per-line tracking, no full type resolution. Blast radius and cycles need nothing deeper, and depth multiplies node count for zero product value.
  • History depthLast 500 commits or 12 months Recency decay means older commits contribute almost nothing anyway. Keeps the clone fast and the graph inside the free tier.
  • AI writes no CypherTool calls over fixed parameterised queries The model picks which query and with what arguments. Every query is one we wrote and tested. This satisfies the assignment's "no string-concatenated Cypher" rule by construction, and it can't hallucinate a traversal that doesn't exist.
  • Chat is not the UIDesigned screens first, chat alongside Design effort is explicitly graded. A chat box over a graph is an API with a text field. The visual map is the product; chat is the escape hatch for questions the screens don't cover.
  • Ingestion is a jobQueue + worker, concurrency 1 Never a request/response cycle. A jobs table and a polling worker is enough — the queue is not what's being graded, and the progress UI it enables is worth more than the queue itself.

01Why a graph database

This section is required in the README and is the thing most likely to be probed in the interview. Drafting the argument now, before writing code, so the model serves the argument rather than the reverse.

The honest framing is not "SQL can't do this" — Postgres has recursive CTEs and at a hundred thousand nodes it would likely be faster. The argument is about which queries stay expressible.

PropertyHow this use case hits it
Depth is chosen at query time "What does this function reach?" is 1 hop or 6, decided by a slider the user drags. In SQL each hop is another join, and you cannot write a query with an unknown number of joins — you write a recursive CTE and hand-manage the frontier, or you loop in application code.
Path semantics, not just reachability shortestPath() between two symbols answers "how does the HTTP handler actually reach the database write?" SQL can tell you whether B is reachable from A. Telling you the route means reimplementing BFS outside the database.
Negative path constraints The single best query in the product: files that change together in commits but have no import path between them at any depth. That's NOT (a)-[:IMPORTS*1..4]-(b) — one clause. The relational equivalent is a recursive CTE inside a NOT EXISTS, per candidate pair.
Heterogeneous, growing edge types Seven relationship types at launch across five node labels, and adding an eighth is a new label rather than a new table plus a migration plus new joins in every existing query.
The graph is the interface The main screen renders the network itself. The user isn't reading a report derived from relationships — they're navigating them directly, and every click is another traversal.

The one-liner for the README. A codebase is not rows — it is a call graph, an import graph, a co-change graph and an ownership graph layered on the same nodes. Every question worth asking is "what is connected to this, and how far does it go" — where how far is the user's choice, not the schema's.

02Data model

Six labels, seven relationship types. Everything is scoped by repoId — that is the tenancy boundary, it is indexed, and every single query filters on it.

Nodes

Two modelling traps, both avoidable.

1. Co-change must be precomputed and filtered. Aggregating it at query time is expensive, and computing it naively produces garbage: a merge commit or a formatting sweep touching 200 files creates 20,000 fake "coupling" pairs. Rule: skip any commit touching more than 30 files, and only persist pairs that co-occurred 3+ times. That single filter is the difference between a signal and a hairball.

2. Bots will own the entire repository. dependabot, github-actions and renovate commit constantly. Flag them at ingest (isBot) and exclude by default, with a toggle to include.

The ownership calculation

Not stored as a property — computed by query, so the decay window stays tunable. For each (Author, File) pair: 

contribution = Σ over commits ( lines_changed × 0.5 ^ (age_days / 180) )
share        = contribution / total contribution for that file

The six-month half-life is the whole point: somebody who wrote a file four years ago and left is not its owner. Cap per-commit lines_changed at ~500 so one giant refactor cannot outweigh fifty careful commits. Bus factor is the standard truck-factor definition — the smallest number of authors whose combined share crosses 50%.

03Ingestion

Three doors into the same extractor. All three produce the identical GraphPayload JSON, which is the only thing the loader ever sees.

3.1

Core

Paste a URL in the web app. It becomes a queued job, never a request/response. The UI streams phases: queued → cloning → parsing → linking → history → writing → ready.

That progress screen is not overhead. Loading states are explicitly graded, and watching a codebase turn into a graph is the best forty seconds of the screen recording.

Stretch · cut first

04The query layer

Eight parameterised Cypher queries. This is the only place Cypher exists in the codebase. Each one gets three front doors — a REST handler for the UI, a tool definition for chat, and an MCP tool — from a single shared definition. 

search(term, kinds?)              → files, symbols, entrypoints matching
neighbors(nodeId, depth, dir)     → what this reaches / what reaches it
path(fromId, toId)                → shortest route between two nodes
who_touched(scope, halfLifeDays)  → ranked authors with weighted contribution
bus_factor(scope)                 → single-point-of-failure modules
co_changed(fileId, minCount)      → files that move together
hidden_coupling(repoId)           → co-change with no structural link
cycles(repoId)                    → import loops
entrypoints(repoId)               → the app's public surface

The three that carry the argument

Hidden coupling — the negative variable-length path. This is the headline query and the one to walk through in the interview.

MATCH (a:File {repoId: $repoId})-[cc:CO_CHANGES]->(b:File {repoId: $repoId})
WHERE cc.count >= $minCount
  AND NOT (a)-[:IMPORTS*1..4]-(b)
RETURN a.path, b.path, cc.count, cc.strength
ORDER BY cc.strength DESC
LIMIT $limit

"These two files always change together, but nothing in the code connects them" — an undocumented contract, invisible to static analysis and invisible to your IDE.

Blast radius — depth chosen by the user, at query time.

MATCH (target:Symbol {repoId: $repoId, id: $id})
MATCH p = (dependent:Symbol)-[:CALLS*1..5]->(target)
WHERE length(p) <= $depth
WITH DISTINCT dependent, min(length(p)) AS hops
MATCH (f:File)-[:DEFINES]->(dependent)
RETURN dependent.name, f.path, f.isTest, hops
ORDER BY hops, f.path

Ownership — aggregation with time decay.

MATCH (a:Author {repoId: $repoId})-[:AUTHORED]->(c:Commit)-[ch:CHANGED]->(f:File)
WHERE f.path STARTS WITH $scope
  AND (a.isBot = false OR $includeBots)
  AND c.fileCount <= 30
WITH a,
     sum(
       (CASE WHEN ch.added + ch.deleted > 500 THEN 500 ELSE ch.added + ch.deleted END)
       * 0.5 ^ ((($now - c.committedAt) / 86400.0) / $halfLifeDays)
     ) AS weight,
     count(DISTINCT f) AS files,
     max(c.committedAt) AS lastTouch
RETURN a.name, a.email, weight, files, lastTouch
ORDER BY weight DESC

Gotcha worth knowing before you hit it. Neo4j-family Cypher does not accept a parameter in a variable-length bound — [:CALLS*1..$depth] is a syntax error. The fix used above: write a fixed generous ceiling (*1..5) and filter with length(p) <= $depth. One query, still fully parameterised, no string concatenation. Find this in phase 3 rather than halfway through phase 4.

Indexes — create these in the schema step, before any load

CREATE INDEX file_repo_path   FOR (f:File)   ON (f.repoId, f.path);
CREATE INDEX symbol_repo_id   FOR (s:Symbol) ON (s.repoId, s.id);
CREATE INDEX symbol_repo_name FOR (s:Symbol) ON (s.repoId, s.name);
CREATE INDEX commit_repo_sha  FOR (c:Commit) ON (c.repoId, c.sha);
CREATE INDEX author_repo_mail FOR (a:Author) ON (a.repoId, a.email);

Load with UNWIND $batch AS row ... MERGE in chunks of ~1,000. One round trip per thousand nodes instead of per node — on a 256 MB instance the difference is minutes versus an hour.

05Surfaces

Three front doors onto the same eight queries. The map is the product, chat is the escape hatch, MCP is the differentiator.

5.1

The map — a big visual representation of the codebase

Core · the centrepiece

The whole repository as a navigable network, filling the screen. Directories as regions, files as nodes sized by lines of code, edges as aggregated imports. This is the screen that makes someone say "oh" out loud, and it's what a hairball-free graph render buys you.

The performance rule that makes it work: the map renders file-level nodes and edges only — never the 30,000 symbol-level CALLS edges. Aggregate imports to file→file with a weight, cap rendered edges to the top N by weight, and drop to symbol level only in the focus view. Ignoring this is how you ship a grey blob.

Colour byOwner · last-touched recency · bus factor · test coverage · directory. A single control that completely changes what the map is saying — cheap to build, reads as depth.
Librarycytoscape.js with the fcose layout — compound nodes give you directory grouping for free. sigma.js if node counts push past ~2,000 and you need WebGL.
InteractionClick a file → side panel with owners (and the evidence), tests, co-change partners, recent commits. Every panel row is another query, not a preloaded blob.
Empty stateNo repo loaded → the three preloaded examples as one-click cards. Nobody ever stares at a blank canvas.
5.2

Focus view — depth slider

Core

Pick any node, drag depth 1→5, watch the affected set grow: symbols, files, tests, and the people attached to them.

This is the screen that demonstrates the "why a graph database" argument rather than asserting it. The reviewer watches an unbounded traversal respond to a slider. Put it in the recording early.

5.3

People view

Core

Who has touched what, with the arithmetic shown. Never a bare score — always "Priya Sharma — 58% of recent weighted changes across 19 files, last touched 3 weeks ago."

Transparency is what makes this usable by a non-engineer and what stops it reading as an AI guess. When it's wrong, the user can see exactly why.

5.4

Chat panel

Core

Sits alongside the map. The model gets the eight tools, composes them, and answers with citations back to tool results. Clicking a citation highlights those nodes on the map.

Composition is the payoff we don't have to build: "if Priya leaves, which entry points are at risk?" becomes bus_factor → neighbors → entrypoints, chained by the model. We never wrote that path.

GuardrailsCap the tool loop at 6 steps. Every claim in the final answer must cite a tool result — no citation, no claim.
ModelGroq's tool-use loop with an open gpt-oss model (OpenAI-compatible API) — cheap and fast; the tool schemas are generated from the same definitions the REST layer uses
5.5

MCP server

High value · cut second-to-last

The same eight tools exposed over MCP. Point Claude Code at your codebase graph and ask it anything, in the editor.

For an agentic-AI company this is the most on-brand thing in the submission, and it costs maybe little because the tool definitions already exist. It also sidesteps text-to-Cypher entirely — the model composes our tested queries instead of inventing its own.

06Architecture

The layering is itself a graded artifact — "clear project structure and a codebase you would be comfortable walking us through line by line." 

cartograph/                            pnpm workspaces (not Turborepo/Bun)
├─ packages/
│  ├─ extract/     repo path → GraphPayload         (no DB, no network)
│  ├─ graph/       GraphPayload → CognoDB; the queries
│  ├─ tools/       one query def → REST + chat + MCP schemas (shared registry)
│  └─ config/      env parsing, fail-fast validation
├─ apps/
│  ├─ cli/         ingest local path, emit JSON or write to DB (= BullMQ processor entry)
│  ├─ api/         NestJS — REST, BullMQ producer + sandboxed worker, chat
│  ├─ web/         React + Vite + Tailwind + shadcn — bubbles map, focus, people, chat
│  └─ mcp/         stdio MCP server over packages/tools
└─ seed/
   ├─ hono.json          pinned demo repo (library)
   ├─ drizzle-orm.json   pinned demo repo (ORM monorepo)
   └─ webapp.json        pinned demo repo (real app: papermark/dub/…, has routes)

The dependency direction is the point: extract knows nothing about the database, graph knows nothing about HTTP, and tools is the single definition that three transports render differently. That is one clean sentence in the README and one clean answer in the interview.

Connection handling

  • Env only. COGNODB_URI, COGNODB_USER, COGNODB_PASSWORD, REDIS_URL, GROQ_API_KEY. A committed .env.example, never a committed .env.
  • Fail fast at boot. Validate env with zod on startup and exit with a readable message, rather than throwing on the first query.
  • One driver instance for the process lifetime, sessions per request. Never a driver per request — 200 connections is the free-tier ceiling.
  • Degrade, don't crash. DB unreachable → the UI shows a real "can't reach the database" state with a retry, not a white screen. This is an explicit requirement and takes twenty minutes.
  • Retry transient failures once with backoff; surface anything else.

Free-tier budget

Target: a ~1,000-file TypeScript repo. Roughly 1k File, 8k Symbol, 30k CALLS, 500 Commit, 50 Author, 5k CHANGED, ~2k CO_CHANGES after filtering. Call it 50–100k nodes and relationships per repo — comfortably inside 0.5 vCPU / 256 MB / 1 GB, and squarely in the range the assignment describes. Three pinned demo repos plus a rolling cache of user ingests, oldest evicted first.

07Phases

Six phases, strictly ordered — each one consumes the previous one's output. Phase 4 is the ship line: once it closes, the project is complete and submittable, and phases 5 and 6 are additive. Every phase has an exit test, so "done" is something you run, not something you feel.

Phase 1

Foundation

Blocking

Prove the database connection and the project skeleton before writing anything that depends on them. A connectivity surprise found here is a nuisance; found in phase 4 it is the submission.

  • Provision the CognoDB c0 instance. Save the password on first display — it is shown once. Write it to .env, commit only .env.example.
  • packages/config — zod schema over COGNODB_URI, COGNODB_USER, COGNODB_PASSWORD, REDIS_URL, GROQ_API_KEY. Parsed at module load; a missing var exits with a readable message naming the variable.
  • packages/graph/src/driver.ts — one neo4j.driver() for the process lifetime, sessions per request, verifyConnectivity() at boot. Never a driver per request.
  • Pin the driver and log the negotiated Bolt version. The assignment specifies CognoDB speaks Bolt 5.0–5.4; a current neo4j-driver may try to negotiate above that. Pin the dependency exactly and print the negotiated version on first connect — an unpinned driver bump is a silent, confusing failure later.
  • packages/graph/src/schema.ts — the five CREATE INDEX ... IF NOT EXISTS statements from §04, exposed as pnpm db:init.
  • Monorepo scaffold: packages/{config,extract,graph,tools}, apps/{cli,api,web,mcp}. pnpm workspaces, shared tsconfig. (Worker is not a separate app — it runs inside apps/api as a sandboxed BullMQ processor.)
  • Dockerfile for ACA — base image must have git installed (node:20-slim / alpine omit it: apt-get install -y git or apk add git). Set the ACA container app to min = max = 1 replica, no scale-to-zero. Provision the free Redis and set REDIS_URL.
Exit test
  • pnpm db:init succeeds, and succeeds again on a second run (idempotent).
  • pnpm db:ping round-trips RETURN 1 and prints the server version.
  • Corrupt the password in .env → a one-line readable error, not a driver stack trace.
Phase 2

Extraction

Blocking

A local repository path in, a GraphPayload JSON out. No database, no network, no HTTP anywhere in this package — that isolation is what makes it testable and what makes the layering argument in the README true rather than aspirational.

  • walk.ts — glob **/*.{ts,tsx,js,jsx}; exclude node_modules, dist, build, coverage, *.d.ts, *.min.js. Mark isTest from path convention, isGenerated from lockfiles and build output.
  • project.ts — ts-morph Project with skipAddingFilesFromTsConfig and skipFileDependencyResolution, no lib files loaded. This is the difference between seconds and minutes.
  • symbols.ts — top-level functions, classes, exported consts, arrow functions assigned to a top-level binding. Capture name, kind, line, exported. Stable id: {path}#{name}.
  • imports.ts — resolve relative specifiers and tsconfig paths aliases to real files. Drop bare package specifiers; external deps are not in the model.
  • calls.ts — every CallExpression, resolve the callee against the file's import map, then local scope. Ambiguous → skip the edge. Track a resolution rate and print it; it is the honest quality metric for the whole extractor.
  • entrypoints.ts — Next.js app/**/page.tsx and route.ts from the path itself; Express/Hono/Elysia from string literals in .get/.post/.put/.delete calls. Literals only — no inference.
  • git.ts — one git log --numstat --no-merges pass with a delimiter-safe --pretty format. Merge author identities via .mailmap, falling back to normalised email. Flag dependabot, renovate, github-actions as isBot.
  • cochange.ts — skip any commit touching > 30 files, then count file pairs, keep count >= 3. Strength normalised so busy files don't dominate: count / sqrt(freqA × freqB).
  • payload.ts — the GraphPayload type and JSON writer. This type is the contract between phases 2 and 3.
Exit test
  • Runs clean against three real repos of different shapes (a framework, an ORM, a library) — not a toy fixture.
  • Node and edge counts land inside the §06 budget; call-resolution rate reported and above ~70%.
  • Spot-check ten CALLS edges against the source by hand. Wrong edges are worse than missing ones.
Phase 3

Graph layer

Blocking

Get the payload into CognoDB, and get the eight queries back out. At the end of this phase there is real data in a real database and every question the product answers is answerable from a terminal — before a single pixel exists.

  • graph/src/load.ts — UNWIND $batch AS row ... MERGE in chunks of 1,000. Fixed order: Repo → File → Symbol → Entrypoint → Author → Commit, then all relationships. One round trip per thousand rows, never per row.
  • graph/src/evict.ts — count nodes per repo; when over budget, DETACH DELETE the oldest pinned = false repo in batches.
  • graph/src/queries/*.ts — one file per query. Each exports { name, description, params: ZodSchema, cypher: string, map(records) }. The zod schema is the single source of truth for validation, REST typing, and the AI tool schema.
  • Write all eight: search, neighbors, path, who_touched, bus_factor, co_changed, hidden_coupling, cycles, entrypoints.
  • packages/tools — convert each zod schema to a JSON Schema tool definition. Written once here, consumed by REST, chat and MCP.
  • apps/cli — ingest <path> with --out, --commits, --repo-id, --pin, --dry-run. This is the seed script the assignment requires.
  • Ingest and pin three repos. Commit the payloads to seed/ so a reviewer can load them without cloning anything.
  • POST /api/query/:name — validate against the zod schema, run, map, return. A single handler serves all eight.
Exit test
  • Three repos loaded and pinned; re-running the loader does not duplicate nodes.
  • All eight queries return sensible results against real data, verified by eye in the CognoDB console.
  • hidden_coupling surfaces at least one pair you can confirm is genuinely coupled — if it returns noise, the phase-2 filters are wrong and this is where you find out.
  • A bad parameter returns a validated 400, not a 500.
Phase 4

Web application

Ship line

The product. Everything here is graded directly — this is where "design effort is explicitly part of the evaluation" gets paid. When this phase closes, deploy and write the README. From that moment the submission is complete and phases 5 and 6 are pure upside.

  • Routes — / repo picker, /r/[repoId] map with side panel, /r/[repoId]/people.
  • The map — cytoscape.js with the fcose layout. Directories as compound nodes, files sized by loc, edges are aggregated file→file imports capped to the top N by weight. Symbol-level edges never render here.
  • Colour modes — owner · recency · bus factor · test coverage · directory. One control that changes what the map is saying; cheap to build, reads as depth.
  • Focus view — select a node, depth slider 1→5, symbol-level neighbourhood. This is the screen that demonstrates the graph argument instead of asserting it.
  • Side panel — owners with evidence, tests, co-change partners, recent commits. Each row is its own query, fetched on demand.
  • People view — never a bare score. Always "58% of recent weighted changes across 19 files, last touched 3 weeks ago."
  • Search — ⌘K over files, symbols and entrypoints.
  • States, built with each screen and not as a later pass — skeletons while querying, empty state offering the three demo repos, an explicit "can't reach the database" banner with retry, and a no-results state that suggests what to try.
Exit test
  • Full click-through on all three seeded repos with an empty browser console.
  • Stop the database mid-session → degraded banner and a working retry, not a white screen.
  • Hand it to someone who has not seen the codebase and watch them find an owner without being told how.
  • Deployed, README written, recording made. Do not carry this into phase 5.
Phase 5

AI surfaces

Additive

Rent the intelligence. The tool definitions already exist from phase 3, so both surfaces are wiring rather than building.

  • Chat — Groq (gpt-oss) tool-use loop over the nine tools, capped at 6 steps so a confused model can't spin.
  • Citations — every tool result carries an id; the answer must reference one per claim. No citation, no claim.
  • Wire citations to the map — clicking a citation chip highlights those nodes. This is the detail that makes chat feel part of the product rather than bolted beside it.
  • apps/mcp — stdio MCP server exposing the identical tool definitions.
  • Screenshot Claude Code querying the graph through MCP. That image belongs near the top of the README.
Exit test
  • Five prepared questions answered correctly with citations, including one that requires chaining two tools the model was never told to chain.
  • Claude Code connects over MCP and answers a question about a seeded repo.
  • Ask something the tools cannot answer → it says so, rather than inventing.
Phase 6

Live ingestion

Additive · highest risk

Turn three preloaded repos into any repo. Deliberately last: it is the riskiest work and the only phase whose failure costs nothing, because the app already shipped in phase 4.

  • Jobs table + worker — poll every 2s, concurrency 1. A queue library is optional; the queue is not what's being graded.
  • Precheck before cloning — GET /repos/{owner}/{repo} for size and language, then the §03 guardrail table. Reject before the user waits, never after.
  • Clone — git clone --filter=blob:none --depth 500 into a temp dir, deleted in a finally.
  • Phase streaming — the worker writes queued → cloning → parsing → linking → history → writing → ready; the UI polls or subscribes.
  • Progress UI — real phase names and counts, not a spinner. This is forty seconds of the screen recording.
  • Rejection states — "This repo is 180 MB; the demo handles repos under 50 MB" with the demo repos offered inline. A designed dead end is not a dead end.
  • Eviction on write — enforce the node budget after each successful ingest.
  • Folder drop — only if everything above is solid. Note in the drop zone that this uploads code, and degrade the ownership views gracefully since a dropped folder has no git history.
Exit test
  • Paste a repo URL you have never ingested → a usable graph, end to end.
  • Paste something oversized, non-TypeScript, and nonexistent → three different, readable rejections.
  • Kill the worker mid-job → the job is retried or marked failed; it never sticks at "parsing" forever.
  • Fresh-clone the repo into a temp directory, follow your own README literally, confirm it runs.

11Explicit non-goals

Things a reviewer might ask about. Having a reason ready is better than having built them.

  • Multi-language support. One extractor done properly beats four done partially.
  • Text-to-Cypher. A cliché, and it fails live. Tools over tested queries is strictly safer and strictly more capable.
  • Persisted risk scores or LLM-named modules. The graph holds facts. Interpretation is the model's job and it changes as models improve.
  • Real-time sync with GitHub. Ingestion is a snapshot. Webhooks are a product, not a take-home.
  • Auth and multi-tenancy. repoId is the only boundary. Adding login would consume the effort that makes the map good.
  • Incremental re-ingest. Re-ingesting is a full rebuild. Correct, simple, and fast enough at this size.

12Submission mechanics

Straight from §6 and §8 of the assignment. Mechanical, easy to get wrong while tired, and each item is a cheap way to lose marks that have nothing to do with the code.

  • Repository. Public by default. If private, invite the reviewers before sending the email, not after they ask.
  • README must contain the use case, a "Why a graph database?" section, the data model diagram, setup and run instructions, the main queries explained, and screenshots of the UI.
  • Setup instructions include creating the CognoDB instance — explicitly called out in the assignment. Walk signup → free c0 → region → connection URI → password, not just bun install. Assume the reader has never used CognoDB.
  • Hosted demo link is mandatory, not optional. So is a short screen recording.
  • Email hr@wexa.ai with the exact subject line: CognoDB Assignment 2 – <Your Name>. Include the repo URL and the demo link.
  • Leave the instance running until you hear back — they may test the app against live data.
  • Dry run before sending. Fresh-clone into a temp directory, follow your own README literally, confirm it runs with no knowledge you already have in your head.

13What the assignment does not say

Everything below is our judgment, not a requirement — invented defaults and elective scope. These are exactly the places a follow-up interview will push, so each one needs a reason rather than a shrug. Listed here so the sourced and the chosen never blur together.

ChoiceStatusThe defence
Chat, MCP, any AI in the product Entirely elective The assignment mentions AI once, as "AI-assisted coding tools" — meaning tools used to write the submission, not features inside it. Nothing asks for an AI product surface. Justify it as the reason the graph can stay facts-only, and be ready to say the app is complete without it.
Six-month ownership half-life Invented Chosen so a year-old contribution is worth ~25% of a fresh one. No source; it is a tunable, which is why it is a query parameter rather than a stored property. Be ready to defend it as a defensible default, not the right number.
Skip commits touching > 30 files Invented Merges and formatting sweeps manufacture false coupling. 30 is a judgment call. Sanity-check it against the seeded repos and adjust with evidence rather than defending the number itself.
Co-change threshold of 3, 500-line commit cap Invented Noise floors. Same defence: tuned against real repos, shown in the README, not pretended to be principled.
TypeScript only Our constraint Nothing in the assignment restricts language. This is a scope decision: one honest extractor over four partial ones.
500-commit history depth Invented Interacts with the decay: at a six-month half-life, commits beyond ~500 contribute close to nothing on an active repo. Weak on a slow-moving repo — acknowledge that rather than defend it.
Node budget of 50–100k per repo Sourced The assignment says "a few thousand to a few hundred thousand nodes and relationships is enough." We sit deliberately inside that band.
Engineering-manager persona Interpretation The assignment says "a non-technical person could use it." We read that as legible without a terminal and without reading source — not as a zero-domain-knowledge user. This is the single most likely thing to be challenged; §05 is the answer, and it must hold up on the recording.

The question to have an answer for. "You built an AI chat and an MCP server — the assignment asked for a graph database application. Why?" The honest answer is that the graph stores only facts, and something has to interpret them; renting that from a model is what let the data model stay clean instead of accumulating scores and labels. If that answer doesn't land, the app still stands on its own without either surface — which is exactly why they are phases 5 and 6.
